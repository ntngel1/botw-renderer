# Wii U shader containers: SHARCB v9

Date: 2026-09-28.Source: proprietary Wii U dump, update `Pack/Bootup_Graphics.pack`.Resource layer selected explicitly; version of executable RPX this study is not installed.Game bytes are not included in Git.

## Implemented instrument

`botw_formats::shader::ShaderArchive` reads **BAHS v9, flags=5, resolved=0** found in the KSys/Agl Wii U archives. It returns programs, macros and their values, binds variants to binary indexes, GX2 reflection (blocks/uniforms/samplers/attributes) and source ranges of vertex/pixel code. It does not recompile or execute anything.

Confirmed fields v9 (little-endian number fields):

- Header: magic `BAHS`, version +4, file size +8, flags +12, resolved +16,
  String-pool size +20. Pool starts with +24; first name is the archive name.
- The pool is followed by the size/count binary array, then the size/count program array.
  Each record starts with its full size. The dimensions don't require four-byte alignment: program records are really unaligned.
- Binary: size +0, stage +4, unknown packed word +8, data size +12
  GX2 payload +16. **Field +8 is not v8 mDataOffset.**
- GX2 program pointer – signed displacement from the beginning of GX2 payload
  Reflection tables are addressed to GX2; their names are offsets relative to archive string pool, not GX2.
- Program: size/name-length/kind/base-index, then name, array macros
  The last two are structurally validated, but their semantics have not yet been restored.
- Macro: size/name-length/value-count/symbol-length, then name in a row
  NUL-terminated values, symbol. Option index is mixed-radix, the last macro changes faster. Kind 3 uses serial VS/PS; kind 8 - stage 3 with unread semantics.

The links between variants and binary counts have been verified across all seven archives, which are structure facts and verifiable interpretations of the resource, not proof that all variants are fulfilled by the game.

## Sources and discrepancies

The local decompilation `botw` commit `5b26254bfe69560b0993a50d8ba8f418ae749380` contains `lib/agl/include/common/aglResBinaryShaderArchive.h`, `aglResShaderBinary.h`, `aglResBinaryShaderProgram.h`, `aglResShaderVariation.h` and handlers in `lib/agl/src/utility/common/aglResShaderArchive.cpp`. **v8** is described there, so these structures provide a guideline, but are not proof of Wii U v9 fields. A similar old scheme is published by the [ study SHARCFB v8](https://github.com/kinnay/Nintendo-File-Formats/blob/master/src/libs/agl/sharcfb.md).

Native GX2 offsets are checked with [WUT shaders.h](https://github.com/devkitPro/wut/blob/master/include/gx2/shaders.h): VS size/program +0xD0/+0xD4, PS +0xA4/+0xA8; structure sizes 0x134/0xE8. The new reader is written independently by dump fields and checks; the code of third-party parsers was not copied.

## Reproduction

A common example takes Yaz0/SARC and repeatable `--entry` to avoid requiring pre-temporary unpacking.The root of the original dump is taken from `renderer.toml`; for layered lookup, select `ContentRoots::find` first.The example below intentionally explores a specific update pack.

```sh
cargo run --offline -p the original format parser --example shader_archive -- \
  "$DUMP_UPDATE/content/Pack/Bootup_Graphics.pack" \
  --entry System/KSys/U-King.Cafe_Cafe_GX2.release.ssarc \
  --entry uking_pass_shader.sharcb --out "$RESEARCH_OUT/uking_pass_shader"
```

`--out` should be outside the repository. Original `archive.sharcb`, `manifest.txt` and indexed `NNNNN-stageN.gx2`/`.code` are written. File names are generated by indexes, not untrusted resource names. Manifest contains the source path, nested, offsets, entry and reflection. Without `--out` , only manifest is displayed.

Local output: `game-data/reference/visual-formulas/shader-archives/`.

## Verifications and limits

`python3 scripts/dev.py check --scope formats`: 99 tests passed, including 6 new synthetic tests: truncation/unsupported header, binary/program range rejection, negative dedup pointer, global reflection name, macro values. All seven real-world archives were successfully disassembled after adding dedup range restrictions. Each code range is placed in one supported GX2 payload after native header; this is not a complete check of non-intersection of all metadata.

Stage 2/3 payload is saved, but code/reflection is not decoded; the example prints explicit unsupported diagnostic. BFSHA, SHARCFB v8, Switch, v9 flags except 5, runtime-resolved pointers are clearly not supported by this reader. Two additional program arrays and packed word are saved without fictitious semantics. Latte disassembler, full validation GPU ISA and runtime choice of options - the next steps. Successful reading does not prove fidelity.

## BFSHA: Wii U FSHA 4.5.0.4

The second reader `shader_bfsha::BfshaArchive` supports strictly `FSHA`, version `0x04050004`, BOM `FEFF`, header size `0x10`. Big-endian numbers; all pointers are signed displacement from the pointer field itself, zero means no. GPU program bytes are saved without byte swap.

Header/model/program layout is restored by reading real pointers and checking all nine product archives. [ShaderLibrary Wii U loader](https://github.com/KillzXGaming/ShaderLibrary/blob/main/ShaderLibrary/WiiU/BfshaLoaderWiiU.cs) was investigated for reference, but its branch of new versions does not directly support headers; the observed BotW layout is different. Reader is written independently, does not translate third-party code line by line. Its model is fixed on version 4.5.0.4:

- Archive: name pointer `+0x14`, model count u16 `+0x24`, model dictionary
  pointer `+0x2C`. Dictionary - size/count and 16-byte nodes (root plus entries), name/value pointers `node+8/+12`; no search tree is required for bypassing.
- Model: static/dynamic key lengths u8 `+0/+1` (U32 words), option counts
  u16 `+2/+4`, program count u16 `+6`; attribute/sampler/block counts
  u8 `+8/+9/+10`. Name pointer `+0x24`, dictionaries static/dynamic options
  `+0x30/+0x38`, attributes/samplers/blocks `+0x40/+0x48/+0x50`, program array
  `+0x58`, packed key table `+0x5C`.
- Program stride `0x4C`; flags u16 `+0`, sampler/block counts u8 `+2/+3`,
  location tables `+0x2C/+0x30`; VS/GS/geometry-copy/PS/compute pointers `+0x34/+0x38/+0x3C/+0x40/+0x44`; parent model `+0x48`. Native VS/PS headers have the usual WUT offsets. Their code pointer is also field-specific (unlike SHARCB).
- Option stride 24: choice count/default u8 `+0/+1`, flags/key-offset/
  word-index/shift u8 `+4/+5/+6/+7`, mask u32 `+8`, choice dictionary `+16`. For full static+dynamic key choice index = `(key[word-index] & mask) >> shift`; choice name is taken in the order of dictionaries. Verified for each option program of all nine resources. This is decoding the saved key; runtime option has not yet been implemented.
- Model reflection is called dictionaries: attribute 4-byte.
  sampler 8-byte, block 16-byte, uniform member 16-byte records. Raw metadata is not issued for restored semantics of unknown type enum. Location tables - four bytes (VS/GS/PS/compute) on binding; `FF` is observed for unused stages. Defaults buffer is not yet readable.

```sh
cargo run --offline -p the original format parser --example shader_bfsha -- \
  "$DUMP_UPDATE/content/Pack/Bootup_Graphics.pack" \
  --entry Shader/uking_mat.product.sbfsha --out "$RESEARCH_OUT/uking_mat"
```

Output: Original `archive.bfsha`, `manifest.txt` (keys, choices, reflection, code ranges), `modelNNN-programNNNNN-vs.code`/`-ps.code`. Names are generated by indexes. The missing stages remain `None`, do not receive a plug; GS/geometry-copy/compute pointers are saved and explicitly marked unsupported.

## Matching a Cemu runtime dump

`tools/research/cemu_shader_matches.py` compares raw `.bin` files emitted by
Cemu against the extracted `.code` files, first by size/SHA256 and then exact
byte equality. Cemu's native dump writer preserves `programCode` bytes; see
[`LatteShader_DumpRawShader`](https://github.com/cemu-project/Cemu/blob/c717fcab1ccc3e0b0b97499a4d9b04a77084e347/src/Cafe/HW/Latte/Core/LatteShader.cpp).
Its output path is the Cemu user-data directory's `dump/shaders` subdirectory.

```sh
python3 tools/research/cemu_shader_matches.py \
  "$RESEARCH_OUT/shader-archives" "$CEMU_USER_DATA/dump/shaders" \
  > "$RESEARCH_OUT/cemu-matches.json"
```

All identical archive candidates remain in the report: shared code does not
identify a unique material or variant. Empty, padded, partial or otherwise
different code remains unmatched; unsupported stages may also be unmatched.
The filename's context-dependent Cemu hashes are not treated as bytecode
identities. A match establishes an encountered program, not draw order,
uniform values, sampler bindings or the final rendered result. The user
controls game launch and shader dumping. Two synthetic tests cover shared
code, partial/padded/empty data and missing inputs. Initial live matches and
the cache-replay procedure are recorded in [Cemu sessions](wiiu-cemu-sessions.md).
